Part 0

What Person A owns

Person A owns the commercial loop that happens inside the company: a rep builds a quote, the engine prices it and explains the risk, a manager and maybe finance approve it, then the quote is sent. Person B takes over once the customer is in the portal.

If you can walk a judge from login → product cost in Settings → Laptop 12% + Setup 18% → “8 pts over” → Manager then Finance → Kanban column “Pending Approval” → approve with a reason → Send, you own this slice.

Person A does not own warehouse splits, proration, invoices, or portal scoping. Those live in Person B. You only need to know that Send sets customerStatus = SENT, and that confirm/fulfillment/payment are later columns.

Part 1

How the code is layered

The repo is one Next.js app. The important rule is: screens do not compute money. A page loads data, a component renders it, a module decides the numbers. If a file under src/app starts adding discounts, it is in the wrong place.

src/ app/(auth)/login, signup ← screens app/(internal)/app/... ← internal screens components/quotes, approvals,... ← React UI modules/pricing, quotes, ... ← business logic lib/auth, money, audit, roles ← shared primitives prisma/schema.prisma ← data model

Why this split exists

Judges will change a discount on a quote and ask “why did it go to Finance?” The answer has to come from a pure function that also has unit tests — not from a React useState total. The same engine runs:

  1. Live in the quote builder (client import of a pure TS function).
  2. Authoritatively on Save / Submit (server re-reads catalog, ignores client prices).
  3. Again on a portal counter-offer (Person B reuses your engine; they do not rewrite pricing).
Convention: modules/*.ts never imports React. app/ never calculates paise. Mutations are Next.js server actions ("use server"), not REST.

Auth, roles, and route guards

Theory: five roles

A user is exactly one of REP, MANAGER, FINANCE, ADMIN, CUSTOMER. Customers always have a customerId (the company they belong to). Internal users must not have one. That invariant is checked when the token is built and when the session is loaded.

  • REP builds and owns quotes. Cannot open Settings or Approvals.
  • MANAGER configures policy, sees Manager steps in the inbox.
  • FINANCE sees Finance steps only after the Manager step is approved.
  • ADMIN can do settings and can override ownership.
  • CUSTOMER is bounced off /app onto /portal.

Signup always creates a REP. Demo passwords are demo1234.

Snippet — two layers of guard

proxy.ts stops a customer hitting /app by URL. That is not enough. Every mutation also calls requireRole, because a logged-in rep could still POST an approve action.

export async function requireRole(roles) {
  const session = await getSession();
  if (!session) unauthorized();
  if (!hasRole(session.role, roles)) forbidden();
  return session;
}

Pages use requireInternal or requirePageRole and redirect. Actions use requireRole and return 401/403. Settings layout additionally requires ADMIN or MANAGER.

Part 3

Money, human codes, and the audit log

Three primitives show up in almost every Person A action. Learn them once.

Money is integers

₹1.00 is stored as 100 paise. 12% is stored as 1200 basis points (bps). The UI shows rupees and percents; the database never stores floats for money. Rounding is half-up, done with integer math, usually once per line.

Directory: src/lib/money.ts

export function formatMoney(paise: number) {
  return inr.format(paise / 100);          // 8500000 → ₹85,000
}
export function parsePercent(value) {
  return Math.round(Number(value) * 100);  // "12" → 1200 bps
}

Human codes

Primary keys are integers. Humans see Q-1042. Quote codes are minted in src/lib/codes.ts. Seeded history starts around 1000 so live demo quotes do not collide.

export async function nextQuoteCode(db) {
  const last = await db.quote.findFirst({ orderBy: { id: "desc" }, select: { code: true } });
  const numeric = last ? Number(last.code.replace(/\D/g, "")) : 1041;
  return `Q-${Math.max(1042, numeric + 1)}`;
}

Audit is part of the transaction

Directory: src/lib/audit.ts. logEvent must run on the same Prisma transaction as the mutation. If save fails, there must be no log line. Person B’s Deal Timeline is simply “all AuditEvents for this quoteId, ordered by time.” If you forget quoteId, the timeline has a hole.

export function logEvent(db, event) {
  return db.auditEvent.create({
    data: { ...event, quoteId: event.quoteId ?? null, meta: event.meta ?? {} },
  });
}

Person A is responsible for logging at least: quote created, line add/update/remove, order discount changed, submitted, auto-approved, approved, returned, rejected, revised, upsell added/dismissed, settings changed, and sent.

Theory: two different kinds of “cheaper for the customer”

  1. Price list (Gold 5% off list) sets the unit price. It is the customer’s catalog price. It is not a discretionary discount and does not consume the 15% Gold ceiling.
  2. Line / order discount is what the rep types. That is governed. Excess over min(tier ceiling, category ceiling) is what creates approval.

Seeded policy (also in docs/policies.md): Bronze 5% / Silver 10% / Gold 15%. Hardware category 15%, Services 10%. Finance if max line excess ≥ 8 pts, or blended excess ≥ 3%, or excess value ≥ ₹5,000.

Part 5

Quote, revision snapshot, four statuses

Schema: prisma/schema.prisma. This is the most important data idea in the product.

Quote vs revision

A Quote is the deal envelope: customer, owner, current revision pointer, and four status columns. A QuoteRevision is a frozen photograph of lines, totals, margin, required approval level, and the reasons[] the engine produced at that moment.

Drafts overwrite the current revision in place (v1 stays v1) until submit. Submit freezes it. “Revise” clones it to v2 and marks v1’s approval steps STALE. Old revisions are never deleted. That is how a judge can ask “what did v1 look like when the manager approved it?”

Prices on a line are snapshots: unitPricePaise, unitCostPaise, tax, discounts, net. Changing the catalog tomorrow must not rewrite Q-1042 v1.

Four independent statuses

Never invent a single “stage” enum. The four columns overlap in time:

ColumnPerson A writesValues you care about
approvalStatusYes — submit / approve / return / reject / reviseNONE, PENDING, APPROVED, REJECTED, STALE
customerStatusSend only (SENT). Draft is the default.DRAFT → SENT → (Person B: NEGOTIATING, CONFIRMED)
fulfillmentStatusNoPerson B
paymentStatusNoPerson B
If you find yourself setting fulfillment inside an approve action, stop. Each event writes only its own column.

Kanban “stage” is derived later from these four. That is Part 10.

Part 6 · the heart of Person A

Pricing engine — detailed theory

Directory:

src/modules/pricing/ engine.ts ← evaluateRevision() (pure) types.ts ← input / output shapes engine.test.ts ← PDF example + edges

evaluateRevision takes a customer tier, the policy row, an order-level discount, and lines. It returns priced lines, totals, margin, three risk signals, a required approval level, and human-readable reasons[]. No Prisma. No React. The UI renders reasons verbatim — that is the product’s explainability, not a separate feature.

Per-line calculation, in order

  1. Unit price is already price-list adjusted when it arrives. Gold’s 5% off list happened before the engine. Do not treat it as discount here.
  2. Base = qty × unit price (paise).
  3. Compounded effective discount. Line 10% and order 10% is not 20%. Remaining fraction = (1 − line) × (1 − order). Effective = 1 − remaining. 10% + 10% → 19% → 1900 bps. The code does this in integer bps with half-up rounding.
  4. Allowed = min(customer tier ceiling, this line’s category ceiling). Gold Hardware: min(15%, 15%) = 15%. Gold Services: min(15%, 10%) = 10%. Bronze Hardware: min(5%, 15%) = 5%. The stricter ceiling always wins.
  5. Excess bps = max(0, effective − allowed). A line inside the ceiling has excess 0 even if it has a discount.
  6. Excess value = base × excess / 10000. This is “how many rupees of unauthorized discount sit on this line.”
  7. Net = base × (1 − effective). Tax = net × tax bps. Cost = qty × unit cost.

Quote-level signals (why Finance exists)

A single huge service breach is easy to see. The brief also cares about many small breaches that hide inside a big hardware quote, and about rupee magnitude.

  • maxLineExcessBps — the worst line. If this is ≥ 800 (8 pts), Finance is required.
  • excessValuePaise — sum of line excess values. If this is ≥ ₹5,000, Finance is required even if no single line is 8 pts over.
  • blendedExcessBps — excessValue / total base. Catches lots of 2–3 pt nicks. Threshold 3% (300 bps).

You must not average discounts across lines. Averaging is the loophole: 18% on a cheap service + 0% on laptops looks “fine” as an average and is not fine as governance.

Margin

Margin is on net revenue excluding tax: margin = netRevenue − cost. Margin % = margin / net revenue. Tax collected is not profit.

Snippet — the actual arithmetic

const remainingBps = roundDiv(
  (10_000 - line.lineDiscountBps) * (10_000 - input.orderDiscountBps),
  10_000,
);
const effectiveDiscountBps = 10_000 - remainingBps;
const allowedDiscountBps = Math.min(tierCeilingBps, line.categoryCeilingBps);
const excessBps = Math.max(0, effectiveDiscountBps - allowedDiscountBps);
const excessValuePaise = roundDiv(basePaise * excessBps, 10_000);
const netPaise = roundDiv(basePaise * (10_000 - effectiveDiscountBps), 10_000);

roundDiv is integer half-up: floor((n + d/2) / d).

Reasons are the UI

For a breaching line the engine emits a sentence like: “Setup Service is 8 pts over the 10% Services ceiling → Manager approval required.” If Finance is triggered it adds “Max line excess 8 pts ≥ 8 pts → Finance approval required.” A clean quote says “All lines within tier and category ceilings → auto-approved.” The last line is always a summary: Requires: No approval / Sales Manager / Sales Manager → Finance.

Tests live in src/modules/pricing/engine.test.ts. The PDF example is the first test: Gold, Laptop 12%, Setup 18% → requiredLevel === "FINANCE" and reasons contain "8 pts over".

Part 7

Approval routing

Directory: src/modules/approvals/route.ts

The engine already computed the three signals. Routing is a tiny pure function so the rule is easy to read and test. FINANCE in this codebase means Manager then Finance, not Finance alone. Sequence 1 is always Manager when any excess exists.

export function routeRevision(signals, policy) {
  if (signals.maxLineExcessBps <= 0) return "NONE";
  if (
    signals.maxLineExcessBps >= policy.financeLineExcessBps ||
    signals.blendedExcessBps >= policy.financeBlendedExcessBps ||
    signals.excessValuePaise >= policy.financeExcessValuePaise
  ) return "FINANCE";
  return "MANAGER";
}
SignalsrequiredLevelSteps created on submit
Every line excess = 0NONENone. Quote becomes APPROVED immediately (auto-approve).
Some excess, none of the finance triggersMANAGEROne step, sequence 1, level MANAGER.
Any finance triggerFINANCEMANAGER seq 1, FINANCE seq 2.

The engine imports this function, so live DecisionPanel and server submit always agree.

Quote lifecycle actions

Directory:

src/modules/quotes/ actions.ts ← create, saveDraft, submit, revise, dismissUpsell queries.ts ← list, getQuoteDetail, getBuilderData schemas.ts ← zod: ids, qty, bps only — never client totals stages.ts ← Kanban derivation

Screens: src/app/(internal)/app/quotations/page.tsx (list), new/page.tsx, [code]/page.tsx (the deal workspace).

Theory: never trust the client

The builder may show a live total. Submit does not save that total. draftSchema accepts quote id, order discount bps, and lines as { productId, variantId, qty, lineDiscountBps }. Server reloads the product, variant extra price, cost, tax, category ceiling, and the customer’s price list, then runs the engine. If a SKU was deactivated, save throws.

1. Create

createQuote requires REP or ADMIN. It mints Q-…, creates revision v1 empty, points currentRevisionId at it, logs QUOTE_CREATED, redirects to the builder.

const created = await tx.quote.create({ data: { code, customerId, ownerId: session.userId } });
const revision = await tx.quoteRevision.create({
  data: { quoteId: created.id, version: 1, createdById: session.userId },
});
await tx.quote.update({ where: { id: created.id }, data: { currentRevisionId: revision.id } });

2. Save draft

Only while approvalStatus is NONE or STALE (editable). Owner-only, unless ADMIN. Replaces lines on the current revision, writes engine totals onto the revision row, logs LINE_ADDED / UPDATED / REMOVED with before/after in meta.

3. Submit

submitForApproval saves first (so the frozen snapshot matches what the rep saw), then in one transaction:

  1. Delete any leftover steps on this revision.
  2. If not NONE, create Manager step; if FINANCE, create Finance step too.
  3. Stamp submittedAt on the revision (locks the builder).
  4. Set quote approvalStatus to PENDING, or APPROVED if NONE.
  5. Audit SUBMITTED with the reason strings; AUTO_APPROVED if clean.
if (evaluation.requiredLevel !== "NONE") {
  await tx.approvalStep.create({ data: { revisionId, level: "MANAGER", sequence: 1 } });
  if (evaluation.requiredLevel === "FINANCE")
    await tx.approvalStep.create({ data: { revisionId, level: "FINANCE", sequence: 2 } });
}
await tx.quote.update({
  where: { id: quote.id },
  data: { approvalStatus: evaluation.requiredLevel === "NONE" ? "APPROVED" : "PENDING" },
});

4. Revise

Editing an already submitted/approved quote is not an in-place edit. reviseQuote marks old steps STALE, clones lines into version+1, sets quote approvalStatus = STALE, logs REVISED. The rep then saves/submits v2, which re-runs the engine and creates fresh steps. v1 remains viewable.

Person B’s portal counter does a similar “new revision + re-route” using the same engine and router. That is why your snapshot shape has to stay stable.

Theory: steps belong to a revision, not to a quote

When v2 is created, v1’s steps become STALE. Finance must not act on a Manager-pending revision. The inbox query encodes that: Finance rows require a sibling Manager step already APPROVED. The action encodes it again: previous sequence must be APPROVED, step must be PENDING, caller role must match the step level (ADMIN may act as either).

A reason of at least 3 characters is required. Governance without a sentence is not governance.

Snippet — inbox gating

export function getApprovalInbox(role, all = false) {

        : {}),
    },
  });
}

Pipeline Kanban

Directories: src/modules/quotes/stages.ts, src/components/quotes/KanbanBoard.tsx, src/app/(internal)/app/pipeline/page.tsx.

There is no drag-and-drop. Dragging would fake a stage. A card sits in a column because of real status. “Switch to table view” is just a link to the quotations list.

Derivation is a priority waterfall. First match wins:

export function deriveStage(quote) {
  if (quote.approvalStatus === "REJECTED") return "Rejected";
  if (quote.paymentStatus === "PAID") return "Invoiced / Paid";
  if (quote.fulfillmentStatus === "FULFILLED") return "Fulfilled";
  if (quote.customerStatus === "CONFIRMED") return "Confirmed";
  if (quote.customerStatus === "SENT" || quote.customerStatus === "NEGOTIATING")
    return "Sent / Negotiating";
  if (quote.approvalStatus === "APPROVED") return "Approved";
  if (quote.approvalStatus === "PENDING") return "Pending Approval";
  return "Draft";
}

That is why Person A’s Submit moves a card from Draft → Pending Approval with no Kanban code of its own, and why Person B’s payment later moves it to Invoiced / Paid without editing this file.

Upsell panel

Directories: src/modules/upsell/suggest.ts (pure), src/modules/upsell/queries.ts, UI src/components/quotes/UpsellPanel.tsx. Pairings are seeded and optionally edited under Settings → Upsell.

The brief wants suggestions from co-purchase history and promotions, not an LLM. Ranking is deterministic:

score = pairing.weight × 10 + coPurchaseCount + (promoted ? 15 : 0)

A suggestion is dropped if it is already on the quote, already dismissed on this revision, or its own margin % is below policy upsellMarginFloorBps (seeded 20%). Top 3 survive.

if (!current.has(pairing.productId) || current.has(product.id)
    || hidden.has(product.id) || marginBps < marginFloorBps) continue;
const score = pairing.weight * 10 + (pairing.coPurchaseCount ?? 0)
  + (product.isPromoted ? 15 : 0);

The builder then re-runs the pricing engine on “current lines + this item at qty 1, 0% discount” so the card can show margin delta in rupees and the resulting quote margin %. Add calls saveDraft with auditAction: "UPSELL_ADDED". Dismiss writes the product id into QuoteRevision.dismissedUpsellIds JSON and logs UPSELL_DISMISSED. After refresh, it stays gone.

Part 14

Worked example you must be able to narrate

Acme is GOLD. Gold price list is 5% off list — that is unit price, not governed discount. Hardware ceiling 15%, Services 10%. Policy finance line excess = 8 pts.

  1. Ravi logs in as REP → identity/actions.ts → lands on /app/dashboard.
  2. New quotation for Acme → createQuote → Q-… v1 DRAFT / approval NONE.
  3. Add Laptop Pro 14 at 12% line discount. Allowed = min(15% Gold, 15% Hardware) = 15%. Excess 0. OK.
  4. Add Onsite Setup Service at 18%. Allowed = min(15%, 10% Services) = 10%. Effective 18%. Excess = 8 pts. Excess value is small, but max line excess 800 ≥ 800 → router returns FINANCE.
  5. DecisionPanel, still before submit, shows Manager → Finance and the sentence with “8 pts over”. This is the USP.
  6. Submit → persist snapshot on v1 → two ApprovalSteps → quote PENDING. Kanban: Pending Approval. Finance inbox is empty (manager has not approved).
  7. Manager approves with a reason → Finance inbox lights up. Finance approves → quote APPROVED. Kanban: Approved.
  8. Ravi clicks Send → customerStatus SENT. Kanban: Sent / Negotiating. Hand off to Person B (portal, confirm, stock, money).

If Ravi instead sets Setup to 10% before submit: excess 0, requiredLevel NONE, submit auto-approves, no inbox row, audit AUTO_APPROVED.

If after approval Ravi clicks Revise: v2 is born, v1 steps STALE, status STALE, v1 still in quote.revisions.
